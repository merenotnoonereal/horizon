# Fabric API mapping ledger

NeoForge 26.3's transfer API is the specification for parts: Fabric transfer maps almost entirely onto its transactions, component-carrying resources and index-based contents. This ledger maps transfer, registries and data if Fabric mods become port targets; event counterparts belong on individual native hooks, except the review notes under [Event counterparts: client lifecycle and ticks](#event-counterparts-client-lifecycle-and-ticks-1014), which record why a reviewed hook has no `fabric` key. It also records the amount conversion: 81,000 droplets per bucket versus 1,000 mB; conversions refuse fractional mB, never round.

This is a porting ledger, not a promise of binary or source compatibility. **Covered** means the named use has a usable counterpart, not that a whole Fabric module is identical. **Planned** means an explicitly identified design or tracker item, not shipped code. **Gap** means the particular semantics have no established equivalent. Multiple statuses on a row distinguish the individual claims.

Reference: Fabric API 26.3 branch at [`2065040b236a0d5ac011bd6a45625dc49579b222`](https://github.com/FabricMC/fabric/tree/2065040b236a0d5ac011bd6a45625dc49579b222) (Apache-2.0); fork main `be1fa0d1ec89d07998e8ea7c72137ce483904d8c` (snapshot, not a current-status guarantee). NeoForge names below refer to its public 26.3 API, not its implementation: [`ResourceHandler`](https://aldak.netlify.app/javadoc/26.3.x/net/neoforged/neoforge/transfer/ResourceHandler.html), [`Transaction`](https://aldak.netlify.app/javadoc/26.3.x/net/neoforged/neoforge/transfer/transaction/Transaction.html), [`TransactionContext`](https://aldak.netlify.app/javadoc/26.3.x/net/neoforged/neoforge/transfer/transaction/TransactionContext.html), and [`SnapshotJournal`](https://aldak.netlify.app/javadoc/26.3.x/net/neoforged/neoforge/transfer/transaction/SnapshotJournal.html). The fork's parts contract is #41 §7. Paths below are relative to the repository.

### The NeoForge floor

The counterpart for most transfer operations is NeoForge-shaped `ResourceHandler<R>` with index-based contents, component-carrying `ItemResource` and `FluidResource`, and nested `host.transaction` (#41 §7 T1–T3). Fabric-specific differences remain in view iteration, `ContainerItemContext` overflow/additional slots and creative/constant contexts, droplets, and `long` amounts.

### Design recommendations for item fluids and energy

1. Keep a place-backed item exchange whose split/overflow is written in the same transaction as the rest of the move; document the different creative, overflow and water-potion behavior rather than calling it Fabric parity. Allow a deliberate provider composition strategy if several mods need to expose one item.
2. Preserve resource components end-to-end for handlers that support them; the game's buckets and a mod block's saved tanks refuse a fluid with components, and a cauldron discards them. Refuse droplets not divisible by 81, never round; address amounts exceeding `u32` before promising lossless Fabric ports.
3. Item fluid and energy handlers take the same `&Transaction` as item and fluid handlers, so one transaction spans them all; keep it that way, including for item exchange overflow.
4. For energy, fork amounts are `u32` and the game's buffer saves an `i32`, with no unit of its own; inspect the chosen Team Reborn release before claiming compatibility. Provide view and filtering adapters only with clearly stated iteration and identity limits.

argument gap as well as their firing-point gaps.

were read for this review. The change is metadata only: no dispatch, tick-time work,
adapter, alias or gameplay change.

## Event counterparts: item models, tints and tooltips (#1014)

Checked against the same Fabric API 26.3 revision,
`2065040b236a0d5ac011bd6a45625dc49579b222`. Fabric line numbers below are at that
revision; Horizon code is cited by function name, under `crates/horizon-client/src/`
unless the file says otherwise.

Scope: `item_tooltip.rs` and the seven item model and item tint hooks —
`item_model_property`, `item_model_range_property`, `item_model_select_property`,
`item_tint_source`, `register_item_tint_sources`, `register_select_item_model_property`
and `register_range_select_item_model_property`. `register_block_tint_sources` is a
block tint hook and is not part of this review. All eight hooks record a gap; no keys
are added.

In the pinned tree, `fabric-item-api-v1`'s client API declares one event that covers
this area, `ItemTooltipCallback.EVENT`; `fabric-rendering-v1`'s client API has no item
model or item tint event, and its only tint API is the static
`BlockColorRegistry.register` for blocks. The item model and tint hooks therefore
share one reason: Fabric API 26.3 declares no event for the moment they describe.

| Horizon hook | Fabric event considered / status | Evidence and porting boundary |
|---|---|---|
| `item_tooltip` | **Gap:** `ItemTooltipCallback.EVENT` | [Item tooltip API][item-tooltip-api] lines 29–46 declare an array-backed event whose javadoc says it fires "after the game has appended all base tooltip lines to the list", passing the stack, its `Item.TooltipContext`, its `TooltipFlag` and the mutable line list; [item tooltip mixin][item-tooltip-mixin] line 38 injects at `ItemStack.getTooltipLines` `RETURN` ordinal 1, the return that has lines (the first return is the no-tooltip one). Horizon's `Game::stack_tooltip_lines` (`game/blocks/stations.rs`) is the port of that method and calls `Game::native_item_tooltip` at its end when its `shown` flag is set, which is the same "a tooltip the stack does not hide" guard; the client side, point after the base lines, and non-cancelling mutable-list behaviour align. Full argument parity is not proven: Fabric passes `Item.TooltipContext`, whereas Horizon passes local player ids, `TooltipDisplay` and advanced/creative flags, with no explicit tooltip-context argument. `ClientHost` cannot be assumed to supply every context operation. The firing coverage does not: Fabric's injection fires at every qualifying `getTooltipLines` call, and vanilla calls that method outside tooltip drawing — its `SessionSearchTrees` builds the search index from every stack's tooltip lines, which the repo's own oracles record as "SessionSearchTrees.getTooltipLines" (`VanillaCreativeTabsExporter.tooltipLines`) and "SessionSearchTrees.updateRecipes" (`VanillaRecipeBookViewOracle`, whose search tree calls `getTooltipLines`). Horizon's hook fires only where the tooltip is drawn (`Game::draw_stack_tooltip_with`, `Game::stack_tooltip`), never for a crossbow's loaded projectile, and Horizon's search reads export strings instead. A Fabric listener's added lines therefore reach the search index and a Horizon listener's do not, so the moments are not the same. No key. |
| `item_model_property` | **Gap:** none; NeoForge counterpart `RegisterConditionalItemModelPropertyEvent` | No Fabric API 26.3 event names an item model property: `fabric-item-api-v1`'s client API declares only `ItemTooltipCallback`, and `fabric-rendering-v1`'s client API has no model property event. The nearest tint API is the static [block color registry][block-color-registry] lines 47–59, registration methods for blocks, not an event and not item models. Horizon's `Env::item_model_property` (`game/interface/item_draw.rs`, the `ItemEnv` implementation the item model resolver in `horizon-assets` asks) answers a namespaced `minecraft:condition` property each time the model picks a branch, with the stack being resolved. No event, so no key. |
| `item_model_range_property` | **Gap:** none; NeoForge counterpart `RegisterRangeSelectItemModelPropertyEvent` | The same search applies: no Fabric API 26.3 event covers a model property, and the static [block color registry][block-color-registry] is the only tint registration in `fabric-rendering-v1`'s client API. Horizon's `Env::item_model_range_property` answers the number for a namespaced `minecraft:range_dispatch` each time it picks a branch. No key. |
| `item_model_select_property` | **Gap:** none; NeoForge counterpart `RegisterSelectItemModelPropertyEvent` | The same search applies: no Fabric API 26.3 event covers a model property. Horizon's `Env::item_model_select_property` answers the string for a namespaced `minecraft:select` each time it picks a case. No key. |
| `item_tint_source` | **Gap:** none; NeoForge counterpart `RegisterColorHandlersEvent.ItemTintSources` | Fabric has no event for an item tint source; [block color registry][block-color-registry] lines 47–59 register block `BlockTintSource`s and factories at init, a static call, and nothing in `fabric-item-api-v1` or `fabric-rendering-v1` takes an item `tints` entry. Horizon's `Env::item_tint_source` answers the ARGB colour of one `tints` entry per stack each time the item resolves — in hand, in a screen and on the ground — and gets the entry's JSON object. Different mechanism, moment and arguments; no key. |
| `register_item_tint_sources` | **Gap:** none; NeoForge counterpart `RegisterColorHandlersEvent.ItemTintSources` | Fabric's nearest call is the same static block registration, which takes the tint layers and the blocks, not a list of item tint source ids collected once before resources load. Horizon's `register_item_tint_sources` (`game/modding/mods/mod.rs`) collects the ids through `Game::native_register_item_tint_sources` at start, before resources load; a `minecraft:model`'s `tints` entry then colours through `item_tint_source`. No event, so no key. |
| `register_select_item_model_property` | **Gap:** none; NeoForge counterpart `RegisterSelectItemModelPropertyEvent` | Fabric API 26.3 declares no event for registering item model properties, and its item model surface has no such registry; the only registration API in reach is the static block tint registry above. Horizon's `register_select_item_model_properties` (`game/modding/mods/mod.rs`) collects the ids through `Game::native_register_select_item_model_property` once at start, before resources load. No key. |
| `register_range_select_item_model_property` | **Gap:** none; NeoForge counterpart `RegisterRangeSelectItemModelPropertyEvent` | As above: no Fabric API 26.3 event and no item model property registry. Horizon's `register_range_select_item_model_properties` (`game/modding/mods/mod.rs`) collects the ids through `Game::native_register_range_select_item_model_property` once at start, before resources load. No key. |

The `item_tooltip` hook remains a gap: the search callers recorded in the repo's
oracles demonstrate different firing coverage, and full tooltip-context argument
parity is not proven. A key requires evidence for all four parts of the contract;
matching the drawing path alone is insufficient.

The change is metadata only: no dispatch, tick-time work, adapter, alias or gameplay
change.

## Event counterparts: loot and drops (#1014)

Checked against the same Fabric API 26.3 revision,
`2065040b236a0d5ac011bd6a45625dc49579b222`. Fabric line numbers below are at that
revision; Horizon code is cited by function name (under
`crates/horizon-client/src/`, or `crates/horizon-world/src/` for the loot
engine) and never by line number.

Scope: `base.rs`'s `loot_table_load`, `loot_drops`, `loot_function` and
`loot_condition`, and the hooks in `block_drops.rs` (`block_drops`),
`living_drops.rs` (`living_drops`, `get_equipment_drop_chance`) and
`living_experience_drop.rs` (`living_experience_drop`). This is the loot part of
`base.rs`, after the server connection, chunk, level, entity load, player
connection, and effects/interaction/damage/chat parts in the earlier sections.
All eight record a gap; none of these reviewed hooks carries a key and none is added.

| Horizon hook | Fabric event considered / status | Evidence and porting boundary |
|---|---|---|
| `loot_table_load` | **Gap:** `LootTableEvents.REPLACE` and `LootTableEvents.MODIFY` | [Loot table events][lt-api] lines 44–94 declare two separate events at one load site: `REPLACE` returns a replacement `LootTable` (or null) and stops the iteration for that table, while `MODIFY` hands every listener a `LootTable.Builder` and returns void; both receive `(ResourceKey<LootTable>, table/builder, LootTableSource, HolderLookup.Provider)`. [Loot util][lt-util] lines 57–70 runs `REPLACE` and then `MODIFY`, and `determineSource` (the same file, below line 70) says whether the file was `VANILLA`, `MOD`, `DATA_PACK` or `REPLACED`. [Resource load task mixin][lt-load-task] lines 49–72 fires them per table resource immediately after that resource is deserialised and before the table enters the registry; [all-loaded mixin][lt-reload-mixin] lines 48–58 fires `ALL_LOADED` after the whole registry load. Horizon has one hook, `loot_table_load` (`collect`, `out = "table"`), applied by `LootData::apply_native_table_loads` in `horizon-world`'s `loot.rs` after `LootData::load` has read every file: it loops the loaded snapshot in id order and calls `native_loot_table_load` for each table, from `Game::load_server_loot` at world open and from `Game::reload_world_tables` on `/reload`. One Horizon invocation both edits the JSON and may replace the table, so it does the two Fabric events' jobs in one moment instead of Fabric's split replace-then-modify pair, and its `DataLoadContext` (`phase.rs`: load origin, registry/fluid lookups, settings and mods) has no per-table `LootTableSource`, so a Fabric listener can ask `source.isBuiltin()` or distinguish an external data-pack source where a Horizon one cannot. The per-table point also runs after the load has built the table map rather than inside the deserialisation call. No key. |
| `loot_drops` | **Gap:** `LootTableEvents.MODIFY_DROPS` | [Loot table events][lt-api] lines 107–115 and 156–164 declare a void callback with `(Holder<LootTable>, LootContext, List<ItemStack>)`; [loot table mixin][lt-table-mixin] lines 47–60 wrap the consumer overload of `LootTable.getRandomItemsRaw`, collect its stacks, invoke the event after that call returns, then forward the edited list to the original consumer. Horizon's `Game::native_loot_drops` (`game/native_hooks/base.rs`) also edits stacks, a `Vec<ItemStack>`, with no item-entity positions, motion or pickup delay. Its `NativeLootDrops` context supplies a table id, dimension, origin, block or entity, player, tool, explosion and `used`, rather than Fabric's table holder and full `LootContext`. It fires at selected gameplay sites: `Game::native_block_loot`, `Game::native_use_drops`, `Game::drop_death_loot` and `Game::drop_leash`. The death call is after table loot, ordinary equipment and some extras were combined, but before an enderman's carried block and a copper golem's preserved equipment are appended; player inventory is handled separately by `Game::drop_death_items`, not this hook. Use and player-associated leash drops can fire it without a table roll. It does not wrap the loot engine's individual rolls, so chest/fishing rolls and nested table evaluation do not each get this Horizon callback. Both callbacks modify stacks without a cancellation return, but firing point, coverage and context arguments differ. No key. |
| `loot_function` | **Gap:** none | Fabric's whole loot API is the table-level set above ([Loot table events][lt-api] lines 44–115); it has no event that dispatches a custom loot function kind at roll time (in Java such a function is a registered codec, not an event). Horizon's `loot_function` (`collect`, `out = "stack"`) fires inside the roll when a table names a function `type` outside `minecraft:` (`horizon_world::loot::native_loot_function`), for every table the item engine rolls, and may change the stack. No Fabric event covers that moment. No key. |
| `loot_condition` | **Gap:** none | Same boundary: Fabric exposes no event for a custom loot condition kind, only table replacement and modification. Horizon's `loot_condition` (`collect`, `out = "holds"`) fires per unclaimed condition kind during a roll (`horizon_world::loot::native_loot_condition`) and the answer decides whether the entry holds. No key. |
| `block_drops` | **Gap:** none; nearest `PlayerBlockBreakEvents.BEFORE` / `AFTER` | [Block break events][pbb-api] lines 44–77 declare `BEFORE` (server only, returns false to cancel the break), `AFTER` (server only, void) and `CANCELED` (void); interfaces lines 86–128 pass `(Level, Player, BlockPos, BlockState, BlockEntity)` and no drops. [Server game mode mixin][pbb-mixin] lines 107–121 fire them at `Block.playerWillDestroy` and `Block.destroy` inside `ServerPlayerGameMode.destroyBlock`, for player breaks only. Horizon's `block_drops` (`cancel`, `out = "cancel"`) fires in `GameLevel::block_drops_ready` (`game/blocks/spill.rs`) after `Block.dropResources` has built the item entities and the experience, before anything spawns; it edits `Vec<NativeItemDrop>` and `experience`, cancels the spawn, and also covers mob breaks, explosions and level-side breaks. The moment (drop list built vs the break call), the coverage and the arguments all differ. No key. |
| `living_drops` | **Gap:** none; nearest `ServerLivingEntityEvents.AFTER_DEATH` | [Server living entity events][sliving-api] lines 88–90 and 153–160 declare `AFTER_DEATH` as a void `(LivingEntity, DamageSource)` notice; [living entity mixin][sliving-mixin] lines 70–73 fire it in `LivingEntity.die` at the `broadcastEntityEvent` call (and [server player mixin][loot-player-death-mixin] lines 76–78 injects at `ServerPlayer.die` TAIL). It is a death notice, carries no drop list, no position and no cancel. Horizon's `living_drops` (`cancel`, `out = "cancel"`) fires from `Game::drop_death_items` after the entity's whole drop list was collected and each item entity was built, passes the list with positions, motion and pickup delay, plus the killing blow and `recently_hit`, and can cancel the drops; an armor stand fires it with an empty list. Fabric has no drop-list event. Point and arguments differ. No key. |
| `get_equipment_drop_chance` | **Gap:** none; nearest `ServerEntityEvents.EQUIPMENT_CHANGE` | [Server entity events][sentity-api] lines 79–84 and 106–108 declare `EQUIPMENT_CHANGE` as a void `(LivingEntity, EquipmentSlot, previous, next)` notice; its javadoc at lines 73–77 describes equipment changes during `LivingEntity.tick` and on level join. [Equipment change mixin][loot-equipment-mixin] lines 36–38 fires at `Map.put` inside `LivingEntity.collectEquipmentChanges`. It reports a completed change, not a death drop chance. Horizon's hook fires in `Game::drop_death_loot` just before each equipment slot's death-drop roll, with the killing blow, `recently_hit`, the stack, the original chance, `preserved` and an editable `chance`; the roll is still drawn whatever the chance. No Fabric event reports that moment. No key. |
| `living_experience_drop` | **Gap:** none; nearest `ServerLivingEntityEvents.AFTER_DEATH` | Fabric has no experience-drop event; the nearest is the same `AFTER_DEATH` notice at [Server living entity events][sliving-api] lines 88–90 and 153–160, which passes no amount and cannot cancel. Horizon's `living_experience_drop` (`cancel`, `out = "cancel"`) fires from `Game::living_experience_drop` in `Game::drop_death_loot` after the vanilla conditions, with the entity, kind, attacking player, `original` and an editable `amount`; a sculk catalyst that takes the experience skips it. No key. |

The Fabric and Horizon points above come from the Fabric mixins/javadoc and
Horizon's own call order; no decompiled 26.3 sources are present in `.local/` to
check vanilla ordering independently. The change is metadata only: no dispatch,
tick-time work, adapter, alias or gameplay change.
